# A little love test ♡

A mobile-first creator and romantic recipient experience built with Next.js, TypeScript, Tailwind CSS, Framer Motion, and Supabase.

## Run locally

Use Node.js 22 or newer.

```sh
npm install
npm run dev
```

Open http://localhost:3000. `/create` is the editor, `/dashboard` manages published tests, `/demo` runs a sample, and `/love/<id>` is the recipient-only experience.

## Personalize in the website

The creator edits names, nickname, anniversary, intro, letter/closing/signature, up to 20 custom questions, all 11 meter reactions and its minimum accepted percentage, bouquet messages, final text, themes and colors. A phone-shaped preview updates immediately; mobile uses a full-screen preview.

Photos support JPEG/PNG/WebP (8 MB each, 20 maximum); video supports MP4/WebM (25 MB); music supports MP3/WAV/M4A (15 MB, playback depends on browser codec support). Videos never autoplay. The sound toggle starts uploaded music, or a gentle synthesized melody when no song is selected. Optional memories/video scenes are skipped when empty.

Draft text auto-saves in localStorage. Draft media is saved as Blobs in IndexedDB, so reloads retain uploads without exceeding localStorage's small quota. Secret words are never saved to the draft. Browser storage permissions and available device space still apply.

## Connect Supabase once

1. Create a Supabase project.
2. Run `supabase/migrations/001_love_tests.sql` in the SQL editor. It creates private tables, a private `love-media` bucket and a rate-limiter function. Public database access is revoked and RLS is enabled.
3. Copy `.env.example` to `.env.local`. Fill in:
   - `SUPABASE_URL`
   - `SUPABASE_SERVICE_ROLE_KEY` (server-only; never use a NEXT_PUBLIC prefix)
   - `LOVE_APP_SECRET` (at least 64 random characters)
   - `APP_ORIGIN` (`http://localhost:3000` locally; exact HTTPS origin when deployed)
4. Generate the application secret with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` and put it in your environment file.
5. Restart the app. Create a test to obtain its persistent `/love/<uuid>` link.

Without this configuration, editing, local drafts and previews work. Publishing returns an explicit setup message and does not create a fake local-only share link.

## Access and media design

Creator identity uses a random, HttpOnly, SameSite cookie. The database stores its SHA-256 digest. There is no login screen; edit/delete access belongs to the browser that created the test. Clearing that cookie loses creator access. Keep it when managing published tests. An account recovery/sign-in system is not included.

All database operations happen in server routes; service-role credentials are never shipped to the browser. API mutations check the request origin. Text is rendered as escaped React text. Payloads, IDs, configuration, media types and sizes are validated. Upload object paths are generated by the server and never derived from a filename.

Uploads go directly to a signed private Storage URL, then are checked by the server for size and file signature before being attached to a test. Recipient media URLs are signed for one hour. Refresh the recipient page if an expired media URL no longer plays. Images/videos/music are accessible only after the secret gate when one is enabled. Secret words use salted scrypt hashes; an expiring HttpOnly unlock cookie is tied to the current hash. Changing the secret invalidates existing unlock cookies. Unlock attempts and creation/uploads are rate-limited through the database.

Deleting first hides the recipient experience, removes all linked Storage objects, and then removes its database row. If Storage cleanup fails, Delete can be retried from the dashboard. An existing bearer media URL can remain in a recipient's browser until the object is deleted. Detached unfinished uploads should be cleaned periodically: inspect `love_uploads` rows with `test_id is null` older than a day, remove their Storage `path` objects first, then remove those rows. Expired `love_rate_limits` rows can also be deleted periodically. Do not delete newly uploaded/unattached objects while a creator is publishing.

## Deploy on Render

The repository contains `render.yaml` for a **Node web service** on the free plan; this is not a static export because it uses server routes.

1. Connect the GitHub repository in Render, create a Blueprint, and select `render.yaml`.
2. Set the four environment variables above in Render. Use your `https://<service>.onrender.com` URL for `APP_ORIGIN` with no trailing slash. Keep `LOVE_APP_SECRET` stable between deployments.
3. Render runs `npm ci && npm run build` and `npm start -- --hostname 0.0.0.0 --port $PORT`.
4. After deployment, verify `/api/setup` reports `configured: true`, then create a test and open its recipient link on another device.

Render's free service may sleep when idle. No disk persistence is required: published content lives in Supabase.

## Validation

```sh
npm run lint
npm run typecheck
npm run build
npx playwright install chromium
# With npm run dev already running:
npx playwright test
```

The default browser suite checks desktop/mobile creation, drafts/media reload, themes, uploads, meter boundaries/geometry and the entire mini-game journey. Publishing tests are skipped unless `TEST_PUBLISHING=1`; they use the **test-only** HTTP double in `tests/support/mock-supabase.mjs`, plus a separately started app with its SUPABASE_URL pointing to `http://127.0.0.1:5055`. This exercises our API routes, cookies, hashing, signed uploads, edits and deletion, but does not verify a real Supabase project's SQL permissions or network connectivity. Run a live create/upload/unlock/delete smoke test after configuring the real service.

Do not deploy the test double. It is not an alternative database and is never imported by the app.

## Original artwork

Cats, roses, bows and envelope SVGs live in `components/Illustrations.tsx`. Styling is in `app/globals.css`. No external stock imagery is required. Default new-test content is in `lib/experience.ts`; creators customize it through the website.
